# Discrepancies and decisions

1. Spec paths have download suffixes: use desktop_companion_spec (1).md and settings_window_spec (4).md; no canonical copies existed.
2. MCP page listing returned only Settings, but direct node 2012:2 exposed TextChat. The user supplied that direct link; both pages are inspected.
3. Older Settings frames have seven-item navigation; Persona specimens have eight. Use the latter and required Ctrl+1–8 order without changing visual styling.
4. RESOLVED by user: anchored bubble pairs with sprite; the full-width bottom text box is for user response. Implement a separate secure input window so its width does not expand the transparent pet window across the display.
5. RESOLVED by user: Figma fonts, designs and colors take precedence over everything. Ship Courier Prime 22 px, blue #7897d6 at 199/255 opacity, 560 px default width, square inset borders and white shadowed text. Direct Figma fill inspection corrected the earlier #647ead assumption; the exported SVG already had the correct fill. All Appearance controls/options/ranges remain present for later customization. Native Settings chrome remains required.
6. Settings 76 is reused for mock reply speed and conversation persistence. Use separate config fields and document identifiers in the coverage inventory.
7. Main §10.8 permits media only for pet, but Settings 215 requires visible-panel microphone preview. Needs an explicitly activation-scoped permission policy; unresolved before STT implementation.
8. Settings 103 defines binary/JSON-base64/JSON-URL response modes while main TTS example lists binary/SSE-base64/JSON-path. Keep the visible options required by Settings and record the technical mapping before provider implementation.
9. Main §9.2 disables image attach for known text-only models; Settings image subsection warns and sends anyway. Architecture/runtime authority is main: gate attachments for positively known unsupported capability; show amber uncertainty for unprobed models.
10. Main mentions step 19 as Persona in changelog, but §14 orders Persona at 18 and packaging at 19; follow the operative numbered build sequence.
11. User expressly selected the full-width bottom chatbox for responses. Ship input width `wide`, interpreted as the display work-area width; retain the required compact and match-bubble choices. This overrides Settings' match-bubble default under the user's visual precedence instruction.
12. Main §4/phase 7 mentions bubble scale 3; Settings control 118 and binding conflict resolutions cap it at 2.5. The persisted schema and acceptance checks use 0.5/1/2.5.
13. Strong Acrylic is not implemented. Main §18.1 expressly permits this; keep the required option visible but unavailable with an explanation in the Appearance panel. The runtime surfaces an explanatory message for imported configurations requesting it. Do not label translucent fill as native Acrylic.
14. RESOLVED by §0.1 runtime precedence: Main §6.3 limits connection-reset retries to one, while Settings 66 offers 0–3 and defaults to 2; §16.3 adds that full schema range without explicitly replacing the runtime limit. Preserve the required schema/options/default. Zero disables resets; all nonzero selections permit at most one reset before the first token. The Model panel visibly explains this cap. No retries follow received tokens or generic 4xx errors. The explicit system-to-developer role negotiation required by §6.4.5 is a separate protocol fallback.
15. Binding C23 preserves all four configured playback modes for every state. The default idle animation loops indefinitely; configured non-looping animations hold their final frame while that state remains active under §3.5. A renderer completion cannot bypass text/audio/dwell lifecycle gates. No random idle scheduling is introduced.
16. Main §18.2 supplies a technical resolution for Settings 140's installed-font dropdown: curated Windows families plus a validated free-text family field. Implement the curated families and bundled Figma fonts in an editable combo; canvas fallback measurement rejects unavailable names. No OS font enumeration is claimed.
17. Figma includes a Settings-wide Dark mode switch absent from the config inventory. Under the user's explicit Figma visual precedence, add `window.settingsDarkMode` (default false), persisted by the same main-owned config writer. It switches only Settings styling. Existing configs receive the default without losing other fields.
18. Electron's `setVisibleOnAllWorkspaces` does nothing on Windows ([official documentation](https://www.electronjs.org/docs/latest/api/browser-window/#winsetvisibleonallworkspacesvisible-options-macos-linux)). Control 7 is retained; actual Windows pinning needs native platform integration in phase 19. The current Electron call alone is not a completed implementation of that requirement.
19. Sprite Pack archives need finite transport bounds in addition to the specified image/frame/cache bounds: compressed ZIP ≤128 MiB, expanded entries ≤256 MiB, ≤2,000 entries and manifest ≤1 MiB. Individual images retain the specified 25 MiB/8,192 px/512-frame limits. Raw sequences also cap input bytes at the greater of 256 MiB and the configured decoded cache budget. These extra resource limits are documented in SPRITES.md and produce explicit rejection rather than partial import.
20. Settings has a mouth frame-count control but no mouth cell-size fields. Import infers square grids with 2–8 cells, otherwise a horizontal strip divided by the configured count; changing a horizontal strip's count recalculates its cell width. Uneven widths are rejected without changing active assets.
21. Sprite import precedes Persona implementation in §14. Phase 11 retains bundled cards inactive and explicitly states that in the native preview. All ask/auto/ignore policy, switching and separate voice consent must be completed in phase 18 before full application acceptance.
22. The allowed sprite dimensions and scale can exceed the current pet-layout IPC/canvas bounds. Large-asset acceptance and bounded viewport rendering remain required before final phase-19 performance acceptance; no config range is silently reduced.
23. Current Anthropic models require selecting Temperature or Top P rather than submitting both. Its transport sends Top P when non-default (≠1), otherwise Temperature; the Model panel explains this mapping. Both specified controls and persisted ranges remain available. Protocol references: [Anthropic Messages](https://platform.claude.com/docs/en/api/messages/create), [streaming](https://platform.claude.com/docs/en/build-with-claude/streaming), [model listing](https://platform.claude.com/docs/en/api/models/list); [Ollama chat](https://docs.ollama.com/api/chat), [NDJSON](https://docs.ollama.com/api/streaming), [model listing](https://docs.ollama.com/api/tags).
24. Main §9 gives a fixed maximum of four attachments, but Settings control 82 explicitly provides 1–10/default 4. Under §0.1's controls/ranges precedence, use the configured limit; retain four as the default. C19 explicitly selects the Settings resize/format options over main's hardcoded 1,568 px. Keep-original still decodes/re-encodes to remove metadata and freezes GIFs as PNG first frames.
25. Attachment decoding adds a 64-megapixel bound to the specified 10 MiB pre-resize limit; normalized images also remain ≤10 MiB. Unsafe or oversized sources are explicitly rejected. This protects the main process when “Do not resize” is selected; it does not silently downscale that option.
26. RESOLVED by user scope change on October 8, 2026: region screenshots and the selector are outside current scope and move to low-priority future features. This supersedes main §9.1's region-capture requirement, phase 13's screenshot-specific acceptance gate and Settings control 17 for the current release. File/clipboard attachments remain in scope and are tested. The screenshot shortcut row is removed; its legacy schema field is retained for compatibility and must not be registered. No selector approval is pending. Voice phases may proceed using phase 13's revised file/clipboard acceptance; no real vision quality acceptance is claimed.
27. Electron 44's clipboard uses asynchronous ClipboardItems/Blobs rather than the removed readImage API. File/clipboard ingestion uses the installed interface and validates Blob size before reading bytes; [official clipboard reference](https://www.electronjs.org/docs/latest/api/clipboard). The Windows acceptance preserves/restores the original clipboard formats.
